## Audit Findings Summary

### FINDING 1 — Missing DATABASE_URL in .env.example (CRITICAL)
**File:** `.env.example`
**Problem:** `DATABASE_URL` is missing. `backend/src/config/env.ts` requires it via Zod (`z.string().min(1)`). Docker Compose builds it from `DB_USER`/`DB_PASSWORD`/`DB_NAME`, but running the backend locally (outside Docker) or running `prisma db push`/`prisma seed` requires a real `DATABASE_URL` in `.env`. Without it the backend crashes on startup.
**Fix:** Add `DATABASE_URL=postgresql://cloudmart:changeme_strong_password@localhost:5432/cloudmart_db` to `.env.example`. Also add `CORS_ORIGIN=http://localhost:5173`.

### FINDING 2 — Frontend type field names are camelCase, Prisma returns snake_case (CRITICAL)
**File:** `frontend/src/types/index.ts`
**Problem:** Every interface uses camelCase (`isActive`, `imageUrls` → `images`, `categoryId`, `priceAtAdd`, `reservedQuantity`, `shippingCost`, `createdAt`, `referenceCode`, `paidAt`, `recipientName`, `postalCode`, `isDefault`). The Prisma-generated JSON response uses snake_case because Prisma uses the schema's field names as-is (`is_active`, `image_urls`, `category_id`, `price_at_add`, `reserved_quantity`, `shipping_cost`, `created_at`, `reference_code`, `paid_at`, `recipient_name`, `postal_code`, `is_default`). Every component that reads these fields currently accesses `undefined`.
**Files affected by cascading field name changes:**
- `frontend/src/types/index.ts` — primary fix location

- `frontend/src/components/product/ProductGrid.tsx` — no direct field access, no change needed
- `frontend/src/components/cart/CartDrawer.tsx` — `item.product.images` → `item.product.image_urls`, `item.priceAtAdd` → `item.price_at_add`

### FINDING 3 — Product list response format mismatch (CRITICAL)
**File:** `backend/src/controllers/product.controller.ts`, `frontend/src/hooks/useProducts.ts`
**Problem:** `product.service.ts:listProducts()` returns `{ data, total, page, limit, totalPages }`. The controller wraps it as `{ success: true, data: { data, total, page, limit, totalPages } }`. The frontend `useProducts` hook types the response as `PaginatedResponse<Product>` which has shape `{ success, data: Product[], pagination: { page, limit, total, totalPages } }`. So `res.data.data` is `{ data: Product[], total, page, limit, totalPages }` — not `Product[]` — and `res.data.pagination` is `undefined`.
The `ProductsPage.tsx` reads `data?.data` (would get the nested `data` array) and `data?.pagination` (undefined → no pagination renders).
**Fix:** Change `product.controller.ts` to reshape the response: return `{ success: true, data: result.data, pagination: { page: result.page, limit: result.limit, total: result.total, totalPages: result.totalPages } }`.

### FINDING 4 — Admin orders endpoint returns paginated object, page reads it as flat array
**File:** `frontend/src/pages/admin/OrdersPage.tsx`
**Problem:** `admin.service.ts:listAllOrders()` returns `{ data, total, page, limit, totalPages }`. The admin controller wraps it as `{ success: true, data: { data, total, ... } }`. But `admin/OrdersPage.tsx` types the response as `{ success: boolean; data: Order[] }` and sets `setOrders(res.data.data)` — getting the pagination object instead of the array.
**Fix:** Admin orders page must extract `res.data.data.data` for the array (or the controller should be fixed to return a consistent shape). Best fix: change the admin controller's `listOrders` to return `{ success: true, data: result.data, pagination: {...} }` (consistent with the product endpoint fix), then update the frontend to read `res.data.data`.

### FINDING 5 — Checkout `addressData` is not handled by backend order controller (CRITICAL)
**File:** `backend/src/controllers/order.controller.ts`, `backend/src/services/order.service.ts`, `frontend/src/hooks/useOrders.ts`
**Problem:** The frontend `useCreateOrder` mutation sends `{ addressData: { recipientName, phone, street, city, province, postalCode }, paymentMethod, notes }`. The backend `order.controller.ts` only destructures `{ addressId, notes, paymentMethod }` from `req.body`. The `addressData` is silently ignored. The order is created with `address_id: null` and no address is saved.
**Fix:** Extend `order.controller.ts` to also read `addressData` from the body. Extend `CreateOrderInput` in `order.service.ts` to accept `addressData?: { recipient_name: string; phone: string; street: string; city: string; province: string; postal_code: string }`. In `createOrder`, if `addressId` is not provided but `addressData` is, create an `Address` record inside the transaction and use its ID.

### FINDING 6 — AdminStats type mismatch: backend returns `revenue`/`orders`/`products`/`customers`, frontend expects `totalRevenue`/`totalOrders`/`totalProducts`/`totalCustomers`
**File:** `backend/src/services/admin.service.ts`, `frontend/src/types/index.ts`
**Problem:** `admin.service.ts:getStats()` returns `{ revenue, orders, products, customers }`. Frontend `AdminStats` interface has `totalRevenue`, `totalOrders`, `totalProducts`, `totalCustomers`. `DashboardPage.tsx` reads `stats.totalRevenue` etc. which are all `undefined`.
**Fix two options (choose the backend fix):** Rename the keys in `admin.service.ts:getStats()` to match: `{ totalRevenue: ..., totalOrders: ..., totalProducts: ..., totalCustomers: ... }`. Also the `recentOrders` field in `AdminStats` is never returned by the backend — the stats endpoint does not include it. Add it to the stats endpoint.

### FINDING 7 — `frontend/src/pages/admin/ProductsPage.tsx` sends wrong payload field names to admin API
**File:** `frontend/src/pages/admin/ProductsPage.tsx`
**Problem:** The form payload uses `categoryId` and `images` as keys: `{ ..., categoryId: form.categoryId, images: [...] }`. But `admin.service.ts:CreateProductInput` and `UpdateProductInput` use `category_id` and `image_urls`. So creating/updating products from the admin UI sends ignored fields and the backend receives `category_id: undefined` → 404 "Category not found".
**Fix:** Change the payload in `handleSubmit` to use `category_id` and `image_urls`.

### FINDING 8 — `backend/src/services/admin.service.ts:updateProduct` ignores `slug` from request body but `createProduct` accepts it implicitly via auto-generation only
No actual bug here, slugs are auto-generated from name on create. But the admin form sends `slug` to the update endpoint and the service ignores it — not a bug but can be confusing.

### FINDING 9 — `useProducts` pagination shape: `data?.pagination` is `undefined` until controller fix
Covered by FINDING 3. After the controller fix, the `ProductsPage.tsx` pagination will work correctly.

### FINDING 10 — `frontend/src/pages/admin/DashboardPage.tsx` uses static `REVENUE_PLACEHOLDER` data for the chart
**Problem:** The revenue chart always shows hardcoded static data regardless of real orders. The stats endpoint does not return time-series revenue data.
**Decision:** The stats endpoint already returns aggregate stats (total revenue, total orders). For the chart, use a simple `recentOrders` list to derive per-day revenue from real data. The backend stats endpoint will be extended to return `recentOrders` (last 10 orders) which the dashboard already has an empty-guard for.

### FINDING 11 — `frontend/src/pages/storefront/CheckoutPage.tsx` calculates subtotal from `item.priceAtAdd` (camelCase) which will be `undefined`
Covered by FINDING 2. After type fix: `item.price_at_add`.

### FINDING 12 — Backend `app.ts` reads `CORS_ORIGIN` from `process.env` directly (not from `env.ts`)
**File:** `backend/src/app.ts`
**Problem:** `cors({ origin: process.env.CORS_ORIGIN || 'http://localhost:5173' })` bypasses the Zod-validated `env` object. This is not broken but inconsistent. Add `CORS_ORIGIN` to `env.ts` schema as optional with default.

### FINDING 13 — `backend/src/services/admin.service.ts:updateProduct` does not update `slug` when name changes
When an admin edits a product and changes only the description, the slug is re-generated from the new name and updates. But if name does not change, `updateData.slug` is not set — this is correct. No bug here.

### FINDING 14 — Missing `ts-node` direct execution config: seed uses `ts-node prisma/seed.ts` but `package.json` has `"db:seed": "ts-node prisma/seed.ts"` which works because `ts-node` is in devDependencies
No bug — `ts-node` is installed. Seed file uses correct snake_case field names (`password_hash`, `image_urls`, `category_id`, `reserved_quantity`). **Seed is correct.**

### FINDING 15 — `frontend/src/pages/admin/OrdersPage.tsx` renders `order.createdAt` (camelCase) instead of `order.created_at`
Covered by FINDING 2.

### FINDING 16 — `Navbar.tsx` calls `useAuthStore().logout()` directly (not `useAuth().logout`) — this skips navigate
In `Navbar.tsx`, the logout button calls `logout()` from `useAuthStore()`, which clears state but does not navigate to `/login`. The `useAuth` hook's `handleLogout` does the navigate. This means after logout in the navbar, the user stays on the same page while unauthenticated — if the page is protected, `ProtectedRoute` will redirect them. This is acceptable behavior. No change needed.

### FINDING 17 — `frontend/src/pages/admin/DashboardPage.tsx` imports `generateOrderId` from `utils` ✓ (exists)

### FINDING 18 — Backend `tsconfig.json` includes only `src/**/*`, excludes `prisma/` — seed runs via `ts-node` directly so this is fine

          city: input.addressData.city,
